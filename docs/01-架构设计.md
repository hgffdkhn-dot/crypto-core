# EnChat 架构设计

> 版本：v0.1（本轮范围：架构 + 核心加密模块 + 协议约定）
> 技术栈：Android（Kotlin + Jetpack Compose + Material3）／服务端（Kotlin + Ktor + PostgreSQL）／共享模块 `crypto-core`

---

## 1. 需求到设计的映射

| 需求 | 设计落点 |
|---|---|
| 原生安卓风格 UI | Compose + Material3（Material You 组件、动态配色），导航用 Navigation-Compose |
| 群聊 / 私聊 / 加好友 / UID / 昵称 / 头像 | `conversations` + `conversation_members` + `friendships`，见 §5 数据模型 |
| 默认加密（客户端↔服务器，到服务器解密成明文落库） | **传输层信封加密**，见 §3.1 |
| 高级加密（端到端），开启后好友列表多一个带锁会话 + 弹窗 | **X3DH-lite + Hash 链棘轮**，见 §3.2 与 §4 |
| 注册/登录：用户名 + 口令（字母/数字/符号） | Argon2id + 服务端 pepper，见 §6 |
| 设置页功能齐备 | 见 §7 |
| 顶部状态条：无网络"正在等待网络…"；有网络未连服务器"连接中…" | 连接状态机，见 §8 |

## 2. 总体架构

```
┌──────────────────── Android 客户端（Compose / Material3）────────────────────┐
│  UI 层：会话列表 / 聊天页 / 联系人 / 设置 / 注册登录                            │
│  状态层：ConnectionState（连接中… / 正在等待网络… / 已连接）                     │
│  领域层：ChatRepository、FriendRepository、KeyRepository                       │
│  安全层：crypto-core（传输层信封 + E2EE 会话 + 群 Sender Key + 口令哈希）        │
│  存储层：Room（消息/会话）＋ Encrypted 存储（身份密钥、会话状态）                │
└────────────────────────────────┬────────────────────────────────────────────┘
                                 │ TLS 1.3 + 应用层信封加密（WebSocket 长连接）
┌────────────────────────────────┴────────────────────────────────────────────┐
│  Ktor 服务端                                                                  │
│  ├ 接入层：WebSocket（/ws）+ REST（/api/v1）                                   │
│  ├ 传输层解密：握手 → 每帧 AES-256-GCM → 明文进入业务层                         │
│  ├ 业务层：账号/好友/群/消息路由/预密钥分发                                      │
│  └ 存储层：PostgreSQL（消息明文或 E2EE 密文）+ 对象存储（头像/文件）             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**`crypto-core` 为什么独立成模块**：Android 与 Ktor 都是 JVM 系，共用同一份密码学实现可避免"两端各写一遍、行为悄悄漂移"这一最常见的加密 bug 来源。该模块只用 `kotlin-stdlib` + BouncyCastle 轻量 API，不依赖 Android SDK。

## 3. 加密策略（核心）

### 3.1 默认加密：客户端 ↔ 服务器传输层

| 层 | 机制 | 目的 |
|---|---|---|
| L1 | **TLS 1.3**（强制，禁用 TLS 1.0/1.1，禁用弱套件） | 防链路窃听与中间人 |
| L2 | **应用层信封加密**（本模块 `TransportCrypto`） | 防 TLS 在网关/负载均衡处终止后的明文暴露；防 APM、日志、抓包组件接触明文 |

握手流程：

```
C → S: clientEphPub(32) || clientNonce(16)
S → C: serverEphPub(32) || serverNonce(16) || Ed25519签名(64)
签名数据 = "ENCHAT-TS-HS-v1" || lp(clientEph) || lp(clientNonce) || lp(serverEph) || lp(serverNonce)

IKM  = X25519(clientEph, serverStaticX25519) || X25519(clientEph, serverEph)
salt = clientNonce || serverNonce
info = "ENCHAT-TS-v1" || lp(clientEph) || lp(serverEph) || lp(clientNonce) || lp(serverNonce)
k_c2s / k_s2c = HKDF-SHA256(IKM, salt, info || "c2s"|"s2c", 36B)  // 32B 密钥 + 4B nonce 前缀
```

每帧：`version(1) || seq(8) || noncePrefix(4) || AES-256-GCM(明文)`
- nonce = `noncePrefix(4) || seq(8)`（12 字节），AAD = `version || seq || channelId(16)`
- 接收方要求 `seq` **严格等于**下一个期望值 → 防重放、防乱序（WebSocket over TCP 是有序流，此约束成立）
- 单连接帧数超过 2^32 必须重新握手（GCM 安全边界）

**到达服务器后**：由业务进程解密成明文并写入 PostgreSQL。这符合"到服务器解密后明文保存"的需求，也意味着**服务器运营方在技术上可以读到普通聊天的明文**——这一点必须在产品内对用户的说明中写清楚（见 §9 威胁模型）。

> ⚠️ 前提：客户端必须以**硬编码 + 证书固定（pinning）**的方式持有服务器长期公钥 `ServerStaticKeys(ed25519Public, x25519Public)`，否则中间人可以用自己的密钥完成握手，L2 形同虚设。密钥轮换需发版或使用多版本 pin 列表 + 平滑过渡。

### 3.2 高级加密：端到端（E2EE）

选型：**X3DH-lite 协商 + Hash 链棘轮 + AES-256-GCM**（用户已确认）。

**为什么不是完整 Signal 双棘轮**：完整双棘轮具备后向保密（密钥泄露后能"自愈"），但引入严格的轮次依赖，异步/乱序/多端场景下极易出现"消息解不开"的体验灾难，且实现与测试成本极高，个人项目极易写出隐蔽漏洞。本方案在"安全强度"与"聊天可用性"之间取平衡点：

| 能力 | 本方案 | 完整双棘轮 |
|---|---|---|
| 前向保密（历史消息不可追溯） | ✅ | ✅ |
| 后向保密（泄露后自愈） | ❌ 需重建会话 | ✅ |
| 乱序/丢包容忍 | ✅ 缓存跳过密钥（上限 1000） | 复杂 |
| 异步离线建立会话 | ✅ 依赖 SPK/OPK | ✅ |
| 服务器可见内容 | 仅密文 + 元数据（谁在何时发给谁、消息大小） | 同 |

**会话建立（X3DH-lite）**

```
DH1 = X25519(alice长期X25519, bob签名预密钥SPK)
DH2 = X25519(alice临时密钥EK, bob长期X25519)
DH3 = X25519(alice临时密钥EK, bob SPK)
DH4 = X25519(alice临时密钥EK, bob一次性预密钥OPK)    // 有 OPK 时

transcript = "ENCHAT-X3DH-v1" || lp(各参与公钥…)
IKM   = 0xFF×32 || DH1 || DH2 || DH3 [|| DH4]
SK    = HKDF-SHA256(IKM, salt=SHA256(transcript), info=transcript, 32B)
```

- Bob 的 SPK 由 Bob 的长期 Ed25519 身份密钥签名 → 服务器无法伪造（但可整包替换，见下）
- Alice 对 `(双方 UID + 双方身份公钥 + EK + SPK/OPK id)` 做 Ed25519 签名 → 服务器无法替换临时密钥做中间人
- **残余风险**：服务器仍可"整包替换"双方公钥包。防线是 **Safety Number**（会话指纹，60 位数字分 12 组）供用户带外比对；这是所有中心化分发密钥的 IM 共有前提，无法仅靠密码学消除。

**每条消息（Hash 链棘轮）**

```
messageKey   = HMAC-SHA256(chainKey, 0x01)
nextChainKey = HMAC-SHA256(chainKey, 0x02)
encKey/nonce = HKDF(messageKey, "ENCHAT-MK-AES-v1"/"ENCHAT-MK-NONCE-v1")
密文        = AES-256-GCM(明文, AAD)
AAD         = version || sessionId || chainIndex || 发送方身份公钥 || 接收方身份公钥
```

- 会话双方各持**两条独立链**（发送链 / 接收链），索引独立计数 → 双向并发收发无需协调
- 消息密钥**一次性**：用过即擦除 → 前向保密
- 乱序到达：接收链预推进，被跳过的消息密钥进缓存（上限 1000），缓存溢出丢弃最旧
- 重放：每条消息密钥只能成功解密一次，解密后立即从缓存移除

### 3.3 群聊加密：Sender-Key

500 人群若对每条消息做 499 次双边加密，客户端与服务器都不可行。采用标准 Sender-Key：

- 每个发送者在每个群持有一条自己的 sender chain；群消息只加密**一次**并广播
- sender chain 的当前链密钥，通过与每个成员的双边 E2EE 会话加密后分发（成员加入 / 密钥轮换时）
- **成员离开或被移除必须提升 epoch 并重新生成 + 重新分发 chain**，否则离开者仍能读后续消息（这是群聊 E2EE 最容易做错的一点）

## 4. "高级加密聊天"的产品行为与技术含义

用户点击好友聊天页右上角设置 → 启用高级加密后：

1. 好友列表/会话列表**新增一个并列会话**（同一好友，带锁图标），与标准加密会话共存，历史消息不迁移
2. 首次进入弹出说明（按需求文案，配锁图标）：

```
🔒  你已开启端到端聊天
    以下功能将会得到加强：
    ✔ 加密增强
    ✔ 卸载软件后聊天将永远不复存在
    ✔ 整体安全系数达到提升
```

**这条文案背后的技术实现（必须做实，不能只是文案）**

| 文案 | 技术保证 |
|---|---|
| 加密增强 | 服务器只存密文；双层加密（E2EE + 传输层） |
| 卸载后消息永远不复存在 | ① E2EE 会话链密钥**只存本地**，绝不上传；② 服务端对 E2EE 消息只存密文 + 有限保留期（默认 30 天，可配）；③ 卸载即密钥销毁 → 服务端残留密文永久不可解；④ 本地数据使用 Android Keystore 保护的密钥加密，卸载后不可恢复 |
| 整体安全系数提升 | 前向保密 + 身份指纹可核验 + 每消息独立密钥 |

> 实现注意：E2EE 会话状态必须写入**受 Keystore 保护**的本地存储；若存进普通 SharedPreferences/DB，root 设备可直接读取，"卸载不复存在"的强度会打折。多设备/云备份会削弱第 ② 条，需在设置中显式告知（默认不做密钥同步）。

## 5. 数据模型（PostgreSQL 初稿）

```sql
users(id BIGSERIAL PK, uid BIGINT UNIQUE, username CITEXT UNIQUE, password_hash TEXT,
      nickname TEXT, avatar_url TEXT, identity_ed25519_pub BYTEA, identity_x25519_pub BYTEA,
      created_at TIMESTAMPTZ, status SMALLINT)

signed_prekeys(id BIGSERIAL PK, user_id BIGINT, spk_id INT, public_key BYTEA,
               signature BYTEA, created_at TIMESTAMPTZ, active BOOLEAN)

one_time_prekeys(id BIGSERIAL PK, user_id BIGINT, opk_id INT, public_key BYTEA,
                 consumed BOOLEAN DEFAULT FALSE, created_at TIMESTAMPTZ)

friendships(user_id BIGINT, friend_id BIGINT, created_at TIMESTAMPTZ, PRIMARY KEY(user_id, friend_id))
friend_requests(id BIGSERIAL PK, from_user_id BIGINT, to_user_id BIGINT, message TEXT,
                state SMALLINT, created_at TIMESTAMPTZ, handled_at TIMESTAMPTZ)

conversations(id BIGSERIAL PK, type SMALLINT,            -- 1=单聊 2=群聊
              encryption_mode SMALLINT,                 -- 1=标准(传输层) 2=端到端
              owner_uid BIGINT, title TEXT, avatar_url TEXT,
              group_epoch INT DEFAULT 1, created_at TIMESTAMPTZ)
conversation_members(conversation_id BIGINT, user_id BIGINT, role SMALLINT,
                     joined_at TIMESTAMPTZ, left_at TIMESTAMPTZ,
                     PRIMARY KEY(conversation_id, user_id))

messages(id BIGSERIAL PK, conversation_id BIGINT, sender_id BIGINT, kind SMALLINT,
         ciphertext BYTEA NULL,        -- E2EE 模式：仅密文
         plaintext  TEXT  NULL,        -- 标准模式：服务器解密后的明文
         e2ee_session_id BYTEA NULL, e2ee_chain_index INT NULL,
         group_epoch INT NULL, created_at TIMESTAMPTZ, server_seq BIGINT)

devices(id BIGSERIAL PK, user_id BIGINT, device_id UUID, identity_ed25519_pub BYTEA,
        last_seen TIMESTAMPTZ)          -- 多设备：v1 先建表，逻辑后续迭代
```

- `server_seq` 单调递增，供客户端断线重连后按序增量同步
- 标准模式的消息保留策略由设置项控制；E2EE 密文默认 30 天后清理（未拉取即删除）

## 6. 注册与登录（用户名 + 口令）

> **本轮已按你的要求放宽：密码不再限定纯数字，允许字母 + 数字 + 常用符号。**

- 用户名：字母开头，字母/数字/下划线，3–32 长度（见 `Protocol.isValidUsername`）
- 口令长度：**8–64**；允许 `a-z A-Z 0-9` 与常见符号，不允许空格与中文
- 策略校验：`PasswordPolicy.validate()`，返回"问题列表 + 0..4 强度分"。拒绝项包括：
  长度不足/超长、非法字符、单字符重复、4 位以上连续递增或递减（`abcd`/`4321`）、
  键盘连排（`qwer`/`asdf`）、内置弱口令黑名单（大小写不敏感）、口令中包含用户名
- 存储：`argon2id` + 服务端 pepper（HMAC-SHA256，pepper 存 KMS/HSM，不入库）

**为什么放宽**：8 位纯数字只有 10^8 ≈ 2^27 种组合，GPU 爆破成本极低，靠 KDF 只能抬高成本、无法根治。
允许字母后同等长度的空间提升到 62^8 ≈ 2×10^14（约 2^47），配合 Argon2id 才有实际意义。

**为什么不做"必须含大小写+数字+符号"的强制组合规则**：NIST SP 800-63B 指出这类规则会促使用户写出
`Password1!` 这种高度可预测的口令。这里只做**结构性**校验（长度、字符集、弱模式），并用强度分引导用户。

```
stored = HMAC-SHA256(pepper, Argon2id(password, salt, m=64MiB, t=3, p=1))
PHC 串：$argon2id$v=19$m=65536,t=3,p=1$<b64 salt>$<b64 stored>
```

> 🟡 **仍需配套的措施**：放宽到字母后熵显著提升，但用户仍可能选 `password123` 这类弱口令。
> 服务端**必须**配套：登录失败限速（按账号 + IP）、异常登录提醒、风控。
> 内置黑名单只覆盖几十条高频样本，**无法替代真实字典检查**；生产建议接入
> Have I Been Pwned 的 k-anonymity 口令范围查询（只传哈希前 5 位，不泄露完整口令哈希）。

## 7. 设置页功能清单（对标主流 IM）

- **账号与安全**：修改密码、用户名/UID 展示与复制、注销账号、登录设备管理
- **个人资料**：头像（压缩后上传，≤2MB）、昵称、个性签名、二维码名片
- **隐私**：加好友验证方式（需验证 / 直接添加 / 拒绝所有人）、黑名单、在线状态可见性、已读回执开关、最后在线时间、"允许通过 UID 搜索到我"
- **消息通知**：新消息通知、免打扰（全局 + 单会话）、声音/振动、通知显示内容（隐藏消息内容）
- **聊天**：字体大小、Enter 键发送、自动下载（Wi-Fi / 移动网络）、聊天背景、表情与 sticker 管理
- **存储与数据**：缓存清理、占用统计、聊天记录迁移（v1 仅标准模式可迁移，E2EE 明确提示不可迁移）
- **加密与安全**：标准/端到端加密说明、**端到端会话列表**、**安全数字核验**、预密钥轮换、清空某会话的本地密钥
- **关于**：版本号、隐私政策、服务条款、开源许可、诊断日志（不记录明文）

## 8. 连接状态机（顶部状态条）

```
                ┌──────────── 无网络（无 Wi-Fi/蜂窝、飞行模式）────────────┐
                ↓                                                          │
        [正在等待网络…]                                              [正在等待网络…]
                │ 网络恢复                                                 ↑
                ↓                                                          │
        [连接中…]  ←── WebSocket 断开 / 握手失败 / 重连退避中 ──→  [连接中…]
                │ 握手 + 鉴权成功                                           │
                ↓                                                          │
            [已连接]  ────────── 鉴权失效 / 被踢下线 ──────────→  [连接失败]
```

判定规则（客户端）：

| 网络可达性 | WebSocket | 展示 |
|---|---|---|
| 无网络 | — | `正在等待网络…` |
| 有网络 | 未连接/握手中/重连退避 | `连接中…` |
| 有网络 | 已连接 + 已鉴权 | 不显示 |
| 有网络 | 明确失败（版本过旧/鉴权失效/被踢） | `连接失败`（附具体原因） |

实现要点：网络可达性用 `ConnectivityManager.NetworkCallback`（不要用过时的 `getActiveNetworkInfo`）；重连用指数退避 + 抖动（1s → 2s → 4s … 上限 30s）；进入前台立即重试一次。

## 9. 威胁模型（能防什么、不能防什么）

| 威胁 | 是否防护 | 说明 |
|---|---|---|
| 链路窃听 / 抓包 | ✅ | TLS 1.3 + 应用层信封双层 |
| 网关 TLS 终止后明文泄露 | ✅ | 应用层信封，业务进程才解密 |
| 服务器被动读取普通聊天 | ❌ | **设计如此**（需求要求服务器明文落库） |
| 服务器读取 E2EE 聊天内容 | ✅ | 只存密文 |
| 服务器伪造用户公钥包（主动 MITM） | ⚠️ 部分 | SPK 需用户签名，但整包替换需靠 Safety Number 发现 |
| 重放 / 乱序注入（传输层） | ✅ | seq 严格递增 + AAD 绑定 |
| 重放 / 重复投递（E2EE） | ✅ | 消息密钥一次性 |
| 拖库后离线爆破口令 | ✅ 较好 | Argon2id(64MiB,t=3) + KMS pepper；口令已放宽到字母，熵显著高于纯数字 |
| 客户端设备被攻破 / root | ❌ | 密钥可能被读出，需 Keystore + 完整性校验缓解 |
| 元数据（谁在何时与谁聊天、消息大小频率） | ❌ | E2EE 不隐藏元数据，需流量填充等高级手段（未实现） |
| 群成员离开后继续读消息 | ✅ | epoch 提升 + sender key 轮换（**必须落实，否则是硬伤**） |

**明确未做（本轮范围外）**：多设备密钥同步、消息撤回/编辑的端到端一致性、密封发送（Sealed Sender）、抗量子（PQXDH）。

## 10. 依赖与体积注意

- `bcprov-jdk18on` 约 8 MB；Android 端必须开启 R8/ProGuard 裁剪，否则 APK 显著膨胀
- 备选实现路径（若将来体积/合规需要替换）：Android 10+ 可用平台 `KeyAgreement("X25519")`、`KeyGenerator` + `AES/GCM`；或换用 libsodium 绑定（lazysodium）
- 本模块所有 BC 调用走 **lightweight API**（不注册 JCE Provider），避免与 Android 自带的裁剪版 BC 冲突
