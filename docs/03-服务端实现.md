## 2. 运行方式

### 2.1 环境变量

| 变量 | 默认值 | 说明 |
|---|---|---|
| `ENCHAT_PORT` | `8080` | 监听端口 |
| `ENCHAT_HOST` | `0.0.0.0` | 监听地址 |
| `ENCHAT_JDBC_URL` | `jdbc:h2:mem:enchat;DB_CLOSE_DELAY=-1` | 数据库连接串（H2 仅用于本地/测试） |
| `ENCHAT_DB_USER` / `ENCHAT_DB_PASSWORD` | `sa` / 空 | 数据库账号 |
| `ENCHAT_DB_POOL` | `8` | 连接池大小 |
| `ENCHAT_PEPPER_B64` | 随机 32 字节 | Argon2id 之后的 HMAC 密钥，**必须由 KMS/HSM 提供** |
| `ENCHAT_SERVER_KEY_FILE` | `./data/server-identity.key` | 服务器长期身份密钥（128 字节） |
| `ENCHAT_UPLOAD_DIR` | `./data/uploads` | 头像存储目录 |
| `ENCHAT_PUBLIC_BASE_URL` | `http://localhost:8080` | 生成头像 URL 用的前缀 |
| `ENCHAT_E2EE_RETENTION_DAYS` | `30` | E2EE 密文保留天数 |

> ⚠️ 默认值只为"本地能跑起来"。生产必须至少覆盖：JDBC 指向 PostgreSQL、pepper 来自 KMS、
> `ENCHAT_PUBLIC_BASE_URL` 指向真实域名。

### 2.2 启动

```bash
# 用 Gradle
gradle :server:run --no-daemon

# 或先构建可执行包
gradle :server:installDist --no-daemon
./server/build/install/server/bin/server
```

首次启动会生成 `data/server-identity.key` 并打印服务器长期公钥：

```
服务器长期公钥（客户端必须 pinning）：
  ed25519=...
  x25519 =...
```

这两个值**必须**编进客户端（或写在证书固定配置里）。换文件 = 所有已装客户端连不上。

### 2.3 沙盒内的离线构建（无 Gradle 时）

```bash
./build-server.sh     # 编译 crypto-core + server，并跑集成测试
```

## 3. 接口

### 3.1 HTTP（JSON，统一 `{ok, err, msg, data}`）

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/health` | – | 健康检查 |
| POST | `/api/v1/auth/register` | – | 注册（用户名 + 口令） |
| POST | `/api/v1/auth/login` | – | 登录，返回 `accessToken` |
| POST | `/api/v1/auth/logout` | ✓ | 注销当前设备 |
| GET | `/api/v1/me` | ✓ | 自己的资料 |
| POST | `/api/v1/me/profile` | ✓ | 改昵称/签名 |
| POST | `/api/v1/me/avatar` | ✓ | 上传头像（base64，≤ 部分见 `Protocol.MAX_AVATAR_BYTES`） |
| GET | `/api/v1/users/{uid}` | ✓ | 按 UID 查用户 |
| POST | `/api/v1/conversations/direct` | ✓ | 打开/创建单聊（指定加密模式） |
| POST | `/api/v1/keys/upload` | ✓ | 上传身份密钥 + SPK + 一批 OPK |
| GET | `/api/v1/keys/bundle?uid=` | ✓ | 取对方公钥包（消费一个 OPK） |
| GET | `/files/{name}` | – | 头像静态文件 |

### 3.2 WebSocket（`/ws`）

**连接生命周期**

1. 客户端发 48 字节 `clientHello`（明文二进制 —— 此时还没有加密通道可用）
2. 服务端回 112 字节 `serverHello`，双方得到 `TransportSession`
3. 客户端发 `AUTH` 帧（`token` + `protocolVersion`）
4. 此后**只接受加密二进制帧**；收到任何 Text 帧一律断开（防止绕过加密层）

**业务帧**（`{t, rid, payload}` 或错误 `{t, ok:false, err, msg, rid}`）

| 方向 | 类型 | 说明 |
|---|---|---|
| C→S | `PING` / S→C `PONG` | 心跳，建议 25s |
| C→S | `AUTH` | 鉴权 |
| C→S | `SEND_MESSAGE` | 发消息（标准模式带 `text`；E2EE 带 `e2ee.ciphertext`） |
| S→C | `MESSAGE_ACK` / `MESSAGE_DELIVER` | 发送确认 / 投递 |
| C→S | `SYNC_REQUEST` | 断线重连增量同步（`afterSeq`） |
| C→S | `FRIEND_REQUEST_SEND` / `FRIEND_ACCEPT` / `FRIEND_REJECT` / `FRIEND_REMOVE` / `FRIEND_LIST` | 好友 |
| C→S | `GROUP_CREATE` / `GROUP_INVITE` / `GROUP_LEAVE` / `GROUP_LIST` | 群 |
| S→C | `FRIEND_REQUEST_EVENT` / `GROUP_MEMBER_CHANGE` | 事件推送 |

## 4. 关键安全设计

### 4.1 加密模式不可降级

`handleSendMessage` 中对端到端会话做了双向约束：

- 会话 `encryption_mode == 2` 时，**只接受密文**；带 `text` 字段直接拒绝（`E2EE_REQUIRED`）
- 标准模式会话也拒绝把明文塞进 E2EE 专用 kind

这样"服务端偷偷把 E2EE 会话当明文存"的路径被堵死。

### 4.2 群成员变动必须轮换链

`GROUP_INVITE` / `GROUP_LEAVE` 都会 `group_epoch + 1`。客户端拿到新 epoch **必须**重新生成 sender key
并逐个分发。否则离群者仍能解后续消息 —— 这是群聊 E2EE 最常见的硬伤。

集成测试里明确断言了这一点：旧 epoch 的接收状态解不开新 epoch 的密文。

### 4.3 Sender Key 分发必须走 1:1 会话

**这是实现过程中发现并修正的一个真实设计问题**：最初把 sender key 消息发到群会话里，
服务端会广播给所有成员，导致其他人收到只该给某人的密钥包（虽解不开，但造成消息错配、也违反最小暴露）。
正确做法是走发起者与每个成员之间的 **1:1 端到端会话**逐一分发。

### 4.4 顺序要求：先分发新链，再用新链发消息

`SenderKeyState.distributionPayload()` 携带的是"链的当前迭代位置"。若先加密消息再分发，
接收方起点会落后于已发出的消息，这批消息将永远解不开。集成测试中的注释已标注。

### 4.5 限速与头像安全

- 限速：注册（IP/小时）、登录（IP + 账号/15 分钟）、好友请求、建群、发消息、密钥上传。阈值集中在
  `RateLimitSettings`，测试环境可整体放宽
- 头像：只接受 JPEG/PNG/WebP；文件名随机 UUID，**拒绝任何含 `/`、`\`、`..` 的路径输入**
- 会话令牌：随机 32 字节，库里只存 SHA-256，可即时吊销（比 JWT 可控）

## 5. 测试覆盖与未覆盖

### 已覆盖（15 项，真实服务端）

注册/登录与各类校验、字母口令存储、登录限速、资料与头像上传（含路径穿越尝试）、
公钥包获取与 OPK 用完即焚、WS 握手 + 鉴权 + 心跳、未鉴权帧被拒、标准模式明文投递与落库、
E2EE 双向消息且服务端只见密文、E2EE 明文降级被拒、乱序投递、群聊 sender key + epoch 轮换、
离线消息同步、好友列表与删除、**客户端持有错误服务器公钥时握手失败**。

### 未覆盖（诚实列出）

| 缺口 | 说明 |
|---|---|
| PostgreSQL 实际跑通 | DDL 分两套维护，H2 版已验证；PostgreSQL 版**未实机执行** |
| 多实例部署 | `RateLimiter` 是单进程内存态，多实例必须换共享计数器（Redis） |
| TLS 终止 | 服务只做应用层加密，TLS 需由 Nginx/Caddy/Ingress 终止 |
| 大规模并发压测 | 沙盒 2 核；未做连接池与 GC 调优 |
| 消息撤回/已读回执 | 协议有 kind 预留，业务逻辑未实现 |
| 文件/图片消息 | 只实现了头像上传 |

## 6. 已知妥协

1. **UID 分配用 `MAX(uid)+1` + 唯一约束重试**：为跨 H2/PostgreSQL 可移植做的不优雅妥协。
   生产建议改用数据库序列（`CREATE SEQUENCE`）。
2. **二进制字段以 Base64 字符串存储**：体积 +33%，换来的是避免 BYTEA/BINARY 的类型差异。
   对密钥（≤96B）与消息（≤8KB）可接受，但大消息场景下不理想。
3. **DDL 未做版本化迁移**：当前是 `CREATE TABLE IF NOT EXISTS` 的幂等建表，
   后续加字段需要手写 ALTER。生产建议引入 Flyway 或 Liquibase。
4. **Argon2 参数是静态的**：测试用 `memoryKiB=1024`，生产用 `64MiB/t=3`。
   真实部署应按压测结果调整，并配合登录限速避免 KDF 成为 DoS 放大器。
